# AI 使用与验证记录

> 记录原则：只写实际发生的事。每条修正都写明“AI 原来怎么做 → 怎么发现 → 改成什么 → 证据在哪”。

## 1. 用到的 AI 工具

| 工具 | 用在哪 |
|---|---|
| Claude Code（Claude 桌面应用，模型 Claude Opus 5.5） | 读题与数据文档、产品与架构设计、编写数据契约、多 agent 并行生成代码与单元测试、真实接口探测脚本、对抗式审查、部署配置、文档 |
| DeepSeek（`deepseek-chat`，OpenAI 兼容接口） | **产品内**的 AI：自然语言→候选条件草案、模糊词澄清选项、语义冲突提示、基于证据的解释文案、自然语言修改条件 |

## 2. 人与 AI 的分工

**候选人决定的事项**
- 产品内大模型选 DeepSeek（国内可直连、成本低、JSON 输出稳定）。
- 部署到 Render 免费 Docker 实例（新加坡区，离数据源与国内评审近），源码放 GitHub 公开仓库。
- 数据源组合：扶摇做筛选与回测主数据；iFinD MCP 只做资讯背景。
- 申请并配置扶摇 / DeepSeek / iFinD 的 Key（只写入本地与部署平台的环境变量）。

**AI（Claude Code）完成的工作**
- 设计规格 `docs/DESIGN.md`、数据契约 `backend/app/schemas.py`、指标目录与规则词典 `backend/app/catalog.py`。
- 用 7 个并行 agent 按契约生成数据层、筛选引擎、回测引擎、AI 层、服务/API、前端并做集成验收；每个 agent 必须让自己负责的单元测试通过。
- 编写并运行真实接口探测脚本，把实测结论写进 `docs/DATA_SOURCES.md`。

**产品运行时 AI（DeepSeek）的边界**：只输出“指标目录内”的条件草案与文案；不产生任何个股数值、不决定入选；输出先经 schema 校验，解释文案再经数字核对与合规清洗，任何一步不通过就降级为规则解析或模板文案（界面上标明）。

## 3. AI 产出中被发现并修正的问题

### 3.1 用真实数据探测发现（2026-10-17，`scripts/probe_fuyao.py`）

AI 最初只依据官方文档（`llms-full.txt`）编写指标映射与数据层约定。拿到真实 Key 后运行探测脚本，发现以下与文档或假设不符之处：

| # | AI 最初的做法 | 实测发现 | 修正 |
|---|---|---|---|
| 1 | 成长类指标按文档字段 `operating_income_yoy_growth_ratio` 等取值 | 实际字段带 `calculate_` 前缀，净利润同比实为**归母**口径（`calculate_parent_holder_net_profit_yoy_growth_ratio`）。按文档取值会让所有成长条件变成“缺失” | 新增 `catalog.INDICATOR_FIELDS` 以实测字段为准，指标更名为“归母净利润同比增长率”；并用利润表自算值交叉核对（茅台 2026H1 自算 −1.9516% vs 接口 −1.951595%） |
| 2 | 回测按 `report_date_ms` 判断某期财报“当时是否已披露” | 历史期的 `report_date_ms` 被后续报告覆盖（茅台 2025Q2 显示 2026-08-15）。照用会让回测把早已公开的财报当成“未披露” | 改用法定披露截止日判断可得性，并写进回测假设 |
| 3 | 行业同业组规则为“成员 ≥ 8 的最细一级” | 行业目录混有二级（90 个）与三级（230 个），三级成员常只有 3–10 家 | 同业组固定用二级行业（881xxx.TI） |
| 4 | 行情/估值时点直接展示信封 `data.timestamp` | 周日运行时 timestamp 为 2026-10-18 03:36，是服务端就绪时间而非成交时间 | 行情时点改为交易日历最后交易日（2026-10-16 收盘），timestamp 作为“接口返回时间”单列 |
| 5 | 估算市值 = 市销率TTM × 营业收入TTM | 茅台用该式比 PE 法低 1.78%（PS 可能按营业总收入计）；再用 iFinD `get_security_indicators` 独立取总市值：茅台 1.6614 万亿、平安银行 2231.68 亿，与 PE 法（16613.6 亿、2231.7 亿）一致 | 主公式改为 PE × 归母净利润TTM，亏损时退回 PS 法，界面标“估算” |
| 6 | 未就绪数据按文档预期为 `3002` 并重试 | 未披露报告期返回 `5003`，按通用规则会每只股票重试 3 次 | 财务指标 5003 只重试 1 次，原因写成“该期可能尚未披露或数据源不可用” |

另记录一处**数据源自身的不一致**：平安银行 2026Q1 加权 ROE 2.83%、扣非加权 ROE 9.15%。产品不把扣非 ROE 用作默认解释，并把它作为“数据冲突”测试样例。

### 3.2 模型选型验证

同一解析任务实测：`deepseek-chat` 3.2 秒、`deepseek-flash` 13.2 秒、`deepseek-v4-pro` 30.6 秒，三者输出的指标 id 都在目录内。交互场景选 `deepseek-chat`。

## 4. 产品内 AI 的验证机制（防止 AI 结果不可信）

1. **封闭词表**：LLM 只能使用 `catalog.py` 登记的指标 id 与算子；未知指标、非法算子、缺阈值的条件被丢弃并在界面提示。
2. **人在回路**：模糊词一律生成澄清选项，AI 默认项可改；自然语言修改只产生“变更清单”，用户点“应用”才生效。
3. **确定性执行**：入选与否只由引擎按公式判定，同输入同输出；AI 不接触个股数值的计算。
4. **数字核对**：AI 写的解释里每个数字都必须能在证据中找到（容差 0.05 或 0.5%），否则丢弃 AI 文本、改用模板。
5. **合规清洗**：输入侧拦截涨跌预测、荐股、收益承诺；输出侧删除买卖建议、目标价、“必涨/稳赚”等表述。
6. **降级可见**：没有 Key、超时或输出不合法时改用规则词典解析，界面标明“规则解析（AI 不可用：原因）”。
